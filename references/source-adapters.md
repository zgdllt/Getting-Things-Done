# 线索来源与回溯设计

## 当前实现形态

GTD 的业务层不直接依赖 Computer History 的文件格式。线索进入系统后经过以下边界：

```text
来源适配器
  → 规范化来源记录
  → 本机 memory 时间覆盖与相关性回溯
  → 候选／问题（SQLite）
  → 用户澄清
  → 预览与明确确认
  → Apple Reminders / Calendar
```

`scripts/gtd_sources.py` 当前包含两个来源能力：

- `ComputerHistoryAdapter` 读取当前 Computer History 的 rolling segments，并将事件转换为统一记录。它是兼容层，不代表 Computer History 提供了稳定的开发者 API。
- `Skysight Markdown memory` 读取 `~/.codex/memories/extensions/skysight/resources/` 中的 10 分钟与 6 小时摘要。时间覆盖当前活动时，摘要优先于原始键盘事件进入模型；当前活动还会检索最多四条有具体词汇重叠的旧摘要，记录为 `computer_history_memory_retro`。

原始事件仍可以保留在本机的持久批次中，用于重试和审计，但摘要覆盖的原始内容不会再次发给模型。回溯摘要只代表历史背景，不能单独创建正式任务、推断截止日期或证明完成。

## 与 GTD 的对应关系

| GTD 环节 | 工作台实现 | 边界 |
| --- | --- | --- |
| 收集 Capture | 来源适配器、快速收集、memory 回溯 | 只保存线索，不表示已承诺 |
| 理清 Clarify | 候选、问题、答复和 Codex 对话 | 用户决定是否承担、结果和下一步 |
| 组织 Organize | 预览后写入已有提醒事项列表；固定时间写入日历 | 模型和回溯都不能越过确认门 |
| 回顾 Reflect | Review 页面和当前工作相关的历史回扣 | 旧线索只能提示检查，不能代替实际清单核对 |
| 执行 Engage | Today 页面和 Codex 的“我有二十分钟”入口 | 选择真实下一步，不按活动频率推断优先级 |

两分钟规则适合做成澄清时的建议：模型可以提示“这件事可能两分钟内完成”，但不自动发送、提交或标记完成。等待、将来／也许、项目和参考资料继续留在候选分类中，直到用户决定去向。上下文标签和参考资料目标需要先确定 Apple Reminders 标签或 Notes／Obsidian 的实际归属，再单独实现。

## Computer History 的替代路线

先保留适配器接口，再按数据质量和隐私成本逐步替换：

1. **短期**：继续使用当前适配器，同时依赖 Markdown memory 做摘要和回溯；增加来源状态、断档提示和可关闭的 memory 来源。
2. **中期**：加入不依赖全量历史的快速收集入口、浏览器扩展和邮件／消息的显式导入。它们输出同样的规范化记录，不要求读取全局键盘流。
3. **长期**：自行开发本地记录器。默认只记录应用切换、窗口／页面标题和用户主动标记的项目；Accessibility、浏览器扩展等权限分别授权；原始文本本机短期保留，摘要和检索索引本机优先。截图、音频和全局键盘记录不应成为默认能力。

自研记录器达到可替代状态前，需要同时满足：能在后台稳定恢复、来源可暂停、可排除应用和网站、记录覆盖范围可见、失败不伪装成“没有任务”，以及候选仍然经过用户澄清和正式写入回执。评价指标应至少包含回溯命中后的用户采纳率、误回扣率、模型调用次数／输入字符量、来源断档时长和重启恢复结果。

## 暂不做的扩展

当前不把“活动频率”当作优先级，不自动执行两分钟事项，不把参考资料复制成第二个任务库，也不在没有明确目标的情况下新增 Calendar 时间块。这些扩展会改变 GTD 的数据归属或用户确认边界，等实际使用中出现稳定需求后再决定。
